## 一、两种构建策略

前端构建工具的核心职责是将源代码编译为浏览器可执行的产物。在这一过程中，Webpack 与 Vite 选择了截然不同的技术路线：

- **Webpack**：启动时从入口出发，递归遍历整个项目的依赖图，将所有模块读取、转译、打包为完整的 bundle，然后交付浏览器运行
- **Vite**：启动时几乎不做编译，仅启动一个本地开发服务器，等浏览器发起请求后，再按需编译被请求的模块

前者是 AOT（Ahead of Time）策略，提前全量编译；后者是 JIT（Just in Time）策略，运行时按需编译。两者的效率差异正是源于这一根本分歧。

理解这一分歧的前提是明确前端工程化中实际存在的两个编译步骤。第一步是打包工具将开发态代码编译为标准代码，例如将 TypeScript 转译为 JavaScript、将 Vue SFC 拆分为脚本与样式、将 SCSS 编译为 CSS。第二步是浏览器拿到标准代码后，经过自身的解析和即时编译（JIT），将 JavaScript 编译为机器码，将 HTML 解析为 DOM，将 CSS 解析为 CSSOM，最终执行渲染。两种构建策略的差异仅存在于第一步，第二步在两种方案中完全一致。

## 二、模块规范与构建策略的关系

两种构建策略的可行性还与代码所采用的模块规范密切相关。目前前端生态中存在两种主流模块规范：CommonJS 和 ES Module。CommonJS 使用 `require()` 和 `module.exports`，是运行时动态加载机制，模块路径可以拼接，加载时机可以嵌套在条件判断中。ES Module 使用 `import` 和 `export`，是编译时静态声明机制，导入语句必须位于顶层，路径必须是静态字符串。

ESM 的静态特性使其在编译时就能确定完整的依赖关系，打包工具据此进行 Tree Shaking，移除未被引用的代码。CommonJS 的动态特性使得依赖关系只能在运行时确定，无法进行有效的静态分析和摇树优化。

两种模块规范与两种构建策略之间存在不同的适配关系。Webpack 配合 CommonJS 可以运行，但无法摇树；Webpack 配合 ESM 可以摇树，但仍需全量预编译，启动响应性较差。Vite 则直接利用了浏览器对 ESM 的原生支持：浏览器解析到 `import` 语句时，自动向服务器发起请求获取对应模块。ESM 的静态分析能力恰好是浏览器能够按需请求的前提，如果换成 CommonJS 的 `require()`，浏览器无法识别该语法，按需加载便无从实现。

因此，ESM 的静态分析与 Vite 的运行时按需加载并非矛盾，而是互相依赖的关系。JavaScript 边编译边执行的特性，使得编译时静态分析与运行时按需加载能够在同一体系中统一。Webpack 的全量预构建和 Vite 的按需即时编译，本质上是对同一个静态分析能力的两种不同使用策略：前者用它来提前遍历整个依赖图，后者用它来让浏览器按需拉取模块。

## 三、Webpack 的工作模式

Webpack 的启动流程是串行的全量处理：

```
启动 Webpack
  → 读取 webpack.config.js
  → 从 entry 出发递归分析所有 import/require
  → 对每个模块调用 Loader 转译
  → 构建完整依赖图
  → 生成 Chunk，执行 Tree Shaking
  → 输出 bundle 到 dist
  → 浏览器加载 bundle
```

在这个过程中，无论开发者本次会访问哪些页面，Webpack 都会将项目中所有模块全部编译一遍。项目规模越大，依赖树越深，启动时间越长。

Tree Shaking 虽然能移除未引用的代码以减小产物体积，但它的前提是已经遍历完整个依赖图，分析的工作量并未减少。换言之，Tree Shaking 优化的是产物大小，不是构建速度。

## 四、Vite 的工作模式

Vite 的启动流程是按需的增量处理：

```
启动 Vite（仅启动 HTTP 服务器）
  → 浏览器请求 index.html
  → 浏览器发现 <script type="module" src="/src/main.js">
  → 浏览器原生 ESM 机制向 Vite 请求 main.js
  → Vite 读取并转译 main.js，返回给浏览器
  → 浏览器解析 main.js 中的 import
  → 逐个向 Vite 请求依赖模块
  → Vite 按需编译，逐个返回
  → ...循环直到所有被引用的模块编译完毕
```

关键在于，浏览器原生支持 ES Module 的 `import` 语法。当浏览器遇到 `import Header from './Header.vue'` 时，会自动向服务器发起一个 HTTP 请求获取该文件。Vite 只在收到请求时才去读取和转译对应文件，没有请求的文件完全不碰。

## 五、效率差异的根源

两种策略的差异可以用一个简单的类比说明：

| 维度 | Webpack（AOT） | Vite（JIT） |
|------|---------------|-------------|
| 启动时做什么 | 全量遍历依赖图 | 仅启动服务器 |
| 谁驱动编译 | 工具主动推送 | 浏览器请求拉取 |
| 编译范围 | 所有模块 | 仅被请求的模块 |
| 项目越大 | 启动越慢 | 启动几乎不变 |

假设一个项目有 1000 个模块，开发者本次调试只涉及其中 50 个。Webpack 需要编译全部 1000 个模块才能启动，而 Vite 只编译这 50 个。两者的工作量相差 20 倍，这就是 Vite 开发启动速度远快于 Webpack 的根本原因。

## 六、适用场景的边界

JIT 策略的优势集中在开发阶段。开发者修改代码后，Vite 只需重新编译改动的那个模块，通过 WebSocket 通知浏览器替换对应模块，实现毫秒级热更新。

生产构建则是另一回事。最终产物需要完整、经过优化、可直接部署到静态服务器，不能依赖运行时按需编译。因此 Vite 在生产环境使用 Rollup 进行全量打包，策略与 Webpack 类似。两者在生产构建阶段的效率差异并不像开发阶段那样悬殊。

所以 Vite 并非在所有环节都优于 Webpack，它的核心优势在于：**利用浏览器原生 ESM 能力，将开发阶段的编译从全量预构建转变为按需即时编译，从而大幅缩减启动时间和热更新延迟。**
