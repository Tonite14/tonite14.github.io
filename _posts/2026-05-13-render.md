首先要回答的问题是何为渲染：

渲染（render）对于浏览器来说，仅代表着一件事，就是将 HTML/CSS 转换为屏幕上像素信息的这一整条完整流水线；对于vue或者react等框架来说，渲染则意味着计算变更后的 UI 应该长什么样（虚拟 DOM），并更新真实 DOM 来匹配这个状态。

```
渲染流水线的大致概念：
HTML 字符串
 → 解析 HTML → DOM 树
 → 解析 CSS → CSSOM 树
 → DOM + CSSOM → Render 树
 → 布局（Layout）：计算每个元素的位置和大小
 → 绘制（Paint）：生成绘制指令
 → 合成（Composite）：拆层、GPU 合成、输出到屏幕
```

而渲染发生的时机，就与事件循环有密切的关联。

对于“输入地址按下回车键后，发生了什么事”这一经典面试题，可以说整个过程主要分为两个阶段，一是网络（拿到html字符串），二就是渲染（解析html）。网络的过程也特别复杂，但这里主要专注于渲染。

网络进程中的网络线程负责拿到html字符串，并生成一个渲染任务交给渲染主线程的消息队列。通过事件循环机制，渲染主线程会提取渲染任务，然后进行渲染流程。

## 解析HTML：

渲染的第一步是解析HTML字符串（字节流）（parse HTML），这个过程会产生DOM树和CSSOM树，树中每个节点都是一个对象，用typeof可以确认这一点，如果想要更进一步查询是什么类型的节点，可以使用instanceof。

```js
const div = document.querySelector('div');
const textNode = div.firstChild; // 文本节点

typeof div; // "object"
typeof textNode; // "object" ← 所有节点都一样

// 进一步判断节点类型
div.nodeType; // 1（元素节点）
textNode.nodeType; // 3（文本节点）

// 或
div instanceof HTMLElement; // true
textNode instanceof Text; // true
```

![image-20260513181333397](/assets/blog_res/2026-05-12-render.assets/image-20260513181333397.png)

严格来说，这里底层形成的dom树是c++的对象结构，而在js操作使用的是js的对象结构，两者并不是完全等同，实际上js操作时会在c++的对象结构上包装一层js（这个包装由绑定层完成，在chrome里是blink引擎执行，V8本身只管执行 JS，它不认识 DOM，`document` 这个对象是 Blink 注入给 V8 的），使得js能够操作。

这一步的关键意义是让后续的步骤不用再直接操作字符串，而是能够操作结构更清晰的dom树。

![image-20260513182454581](/assets/blog_res/2026-05-12-render.assets/image-20260513182454581.png)

cssom的树形结构：

cssom也是对象结构，根节点代表着网页中所有的样式表（\<style>内部样式表，\<link ...>外部样式表，浏览器默认样式表等等，\<div style="">内联样式严格来说不属于 `document.styleSheets`，不存在于 CSSOM 的树结构中。它是 DOM 元素上的 `element.style` 属性，在样式计算（style recalculation）这一步和 CSSOM 规则一起参与层叠，算出最终值），根节点会下边对应产生相同数量的节点。

> 样式表按来源可以分为三种：
>
> | 类型               | 来源                                                       | 在 CSSOM 中的位置                                 |
> | :----------------- | :--------------------------------------------------------- | :------------------------------------------------ |
> | **用户代理样式表** | 浏览器自带（比如 `<h1>` 默认加粗、`<a>` 默认蓝色加下划线） | `document.styleSheets` 不暴露，但对开发者工具可见 |
> | **用户样式表**     | 用户自定义（很少用，浏览器扩展也算）                       | 普通 JS 无法访问                                  |
> | **作者样式表**     | 网页开发者写的                                             | `document.styleSheets` 可遍历                     |
>
> 作者样式表又分三种形式：
>
> ```html
> <!-- 1. 外部样式表 -->
> <link rel="stylesheet" href="style.css">
> 
> <!-- 2. 内部样式表 -->
> <style>
>   body { margin: 0; }
> </style>
> 
> <!-- 3. 内联样式 -->
> <div style="color: red;">hello</div>
> ```
>
> 但内联样式不在 CSSOM 树里，它直接挂在 DOM 节点的 `element.style` 上，不参与样式表的规则层叠，只参与最终计算。
>
> 所以 CSSOM 树实际管理的是外部样式表和内部样式表。用户代理样式表的具体样式可以在blink源码中查看。

js不仅可以操作dom，也可以操作cssom，即外部样式表和内部样式表，内联样式通过dom树操作，最后也参与在cssom的更新。

![image-20260513182426915](/assets/blog_res/2026-05-12-render.assets/image-20260513182426915.png)

已知HTML字节流是包含一般标签的一般内容和css代码的，也已知parse阶段会生成dom和cssom，所以对于一般的dom节点和带有css内容的部分的处理肯定是具有不同的。那么在HTML解析过程中遇到css代码会怎么办？

为了提高解析效率，浏览器会启动一个**预解析器**（这里的解析与主线程的解析含义不同，可以理解为下载）率先下载和解析css。而渲染主线程在遇到css相关内容时，因为已知预解析线程在处理相关数据，会跳过css的相关内容，继续往后解析，直到预解析线程完成解析，就合并入cssom。

> 准确来说，预解析器（Preload Scanner）的职责仅限于**扫描 HTML 中的外部资源链接并提前发起网络请求**，它既不解析 CSS 内容，也不构建 CSSOM 树。CSS 的解析和 CSSOM 树的构建仍然由渲染主线程在后续步骤中完成。
>
> ```text
> HTML 字节流进入后：
>   主线程：逐 Token 解析 HTML，构建 DOM 树
>           遇到 <link href="style.css"> → 通知预解析器
>           继续解析后续 HTML（不等待 CSS 下载）
>   
>   预解析器（独立线程）：
>           扫描到 rel="stylesheet" 的链接 → 立即发起 HTTP 请求
>           扫描到 <script src="app.js"> → 立即发起 HTTP 请求
>           扫描到 <img src="photo.jpg"> → 立即发起 HTTP 请求
>   
>   CSS 文件下载完成后：
>           主线程暂停 HTML 解析？ → 不暂停
>           主线程开始解析 CSS 内容，构建 CSSOM 树
> ```
>
> **关键区分**：预解析器只做“下载”这件事，不做“解析”。CSS 的解析和 CSSOM 的构建始终在主线程上完成。这与 JS 不同，JS 的下载可以由预解析器发起，但 JS 的解析和执行必须在主线程上暂停 HTML 解析后进行。

因为有了不同线程（这些不同线程由浏览器负责）的参与，css代码不会阻塞html的解析。

![image-20260514005742631](/assets/blog_res/2026-05-12-render.assets/image-20260514005742631.png)

在谈论完dom和cssom后，HTML字节流中还有一个重要内容，就是JS代码，JS代码并不和dom与cssom一样，可能后续需要多次更新，JS代码只执行完毕一遍即可。

又因为JS代码有可能修改当前已有的dom，dom树是一边解析一边动态生成的，所以dom树最高效的修改方式当然是让js先执行完再确立最后的dom，不必在渲染完成后再根据js修改dom造成返工。因此在解析过程中如果遇到JS代码，渲染主线程必须暂停一切行为，等待下载完毕，并启动v8执行完js后再继续。

在这个过程中预解析线程会分担一部分的下载负担（例如引用外部js时）。

![image-20260514013520784](/assets/blog_res/2026-05-12-render.assets/image-20260514013520784.png)

## 样式计算：

经过HTML Parser后，得到了dom树和cssom树，下一步就是根据两棵树进行样式计算（Recalculate Style）。经过样式计算后，每个节点就具有了最终的完整的，即计算后的样式（Computed Style）。

> 样式计算的核心是**层叠（Cascade）**，它按照以下优先级顺序决定每个属性的最终值：
>
> ```text
> 用户代理样式表（浏览器默认样式）
> ↓ 如果作者样式表未覆盖，则保留
> 作者样式表中的外部样式表和内部样式表
> ↓ 按选择器特异性（Specificity）比较
> 作者样式表中的内联样式（element.style）
> ↓ 特异性最高
> !important 声明
> ↓ 反转上述优先级顺序
> ```
>
> ```html
> <style>
> .card { color: blue; font-size: 16px; }
> div.card { color: green; }
> div { color: red !important; }
> </style>
> <div class="card" style="color: orange;">文本</div>
> ```
>
> 层叠过程：
>
> ```text
> 1. 用户代理样式表：<div> 默认 color: initial（通常是 black）
> 2. 作者样式表 .card：color: blue（特异性 0,1,0）
> 3. 作者样式表 div.card：color: green（特异性 0,1,1，更高）
> 4. 内联样式：color: orange（特异性 1,0,0，更高）
> 5. !important 声明：div { color: red !important; }（反转优先级）
> 
> 最终结果：color: red（!important 胜出）
> ```
>
> 样式计算完成后，每个节点上的每个 CSS 属性都有一个确定值。这个值存储在 Computed Style 中，供布局阶段使用。

虽然我们设置的样式值往往不超过十个，但此时每一个样式都会具有自己的值，这个最终值的决定就涉及了css属性值的计算过程（css两块最重要的知识就是css属性的计算过程和视觉格式化模型）。

完成之后，会得到一棵带有样式的dom树。

![image-20260514014405686](/assets/blog_res/2026-05-12-render.assets/image-20260514014405686.png)

## 布局：

保证每个节点都具有全部的css样式之后，就会进入布局阶段。这一阶段会根据每个节点的样式来算出它们各自的尺寸和位置。布局计算规则可能非常复杂，主要涉及视觉格式化相关的知识（包含块等）。

这棵布局树并不是dom树，其中的节点也不是dom节点对象，而是c++对象，js是无法获取的。

![image-20260514015606370](/assets/blog_res/2026-05-12-render.assets/image-20260514015606370.png)

布局得到的树与dom树不一定是一一对应的，有些隐藏的元素（例如head、link和meta等标签，chromium源码中的默认样式表设置是display: none）不具备几何信息，即尺寸和位置，不会出现在布局树中。

![image-20260514020527973](/assets/blog_res/2026-05-12-render.assets/image-20260514020527973.png)

布局树的元素也可能相对dom树增加，例如使用::before时，因为引入了新的几何信息。

![image-20260514020536574](/assets/blog_res/2026-05-12-render.assets/image-20260514020536574.png)

这里的节点差异涉及了两个规则：内容必须在行盒中，行盒不能和块盒相邻。根据内容必须在行盒中的要求，在文本a和c之前会生成匿名行盒。

![image-20260514020952529](/assets/blog_res/2026-05-12-render.assets/image-20260514020952529.png)

## 分层：

分层的目的是降低每次页面更新时的更新量，可以理解成每次渲染更新时只更新页面上需要更新的层，而其他层无需改变，从而降低开销。在以前的浏览器的没有这个功能的，现代浏览器才具备。

![image-20260514143057415](/assets/blog_res/2026-05-13-render.assets/image-20260514143057415.png)

这一层的相关信息可以在开发者工具查看（layers工具，中文名为图层）。层次不会划分得特别多，每个浏览器的划分策略都不同，可能非常复杂。

跟堆叠上下文有关的属性（z-index、opacity等）可能会影响到分层结果。开发者无法直接控制层的形成，但可以通过嵌入css等方式来提示浏览器分层（will-change），形象的理解可以类比于告诉浏览器这个元素我会频繁更新，因此浏览器为便于更新元素，可能会对这个元素进行单独分层。但对于这个策略不能滥用，因为我们常常无法保证自己设置的策略的效率会优于浏览器的默认策略，而我们采用分层的目的也恰恰只是为了提高效率。一般只在排查问题时发现渲染速度慢就是因为浏览器的分层策略不足时，我们才会引导浏览器进行分层。

> 分层（Layerization）与堆叠上下文（Stacking Context）密切相关，但并非完全等同。以下属性或条件会**强制创建独立合成层**：
>
> | 触发条件          | 示例                              | 说明                             |
> | ----------------- | --------------------------------- | -------------------------------- |
> | 3D 变换           | `transform: translateZ(0)`        | 任何 3D 变换都会强制提升为合成层 |
> | 硬件加速属性      | `opacity` 动画、`filter` 动画     | 动画过程中的元素会被提升         |
> | 特定 HTML 元素    | `<video>`、`<canvas>`、`<iframe>` | 这些元素天生独立层               |
> | `will-change`     | `will-change: transform`          | 提示浏览器提前创建层             |
> | `position: fixed` | 某些浏览器实现                    | 固定定位元素可能独立成层         |
> | 被裁剪的子元素    | `overflow: scroll` 的子元素       | 滚动容器可能独立成层             |
>
> **滥用合成层的代价**：
>
> 每个合成层都需要占用 GPU 内存（纹理）。在移动端低端机型上，过多的合成层会导致：
>
> - GPU 内存耗尽，页面崩溃
> - 纹理上传带宽饱和，帧率下降
> - 层间合成开销增加，反而降低性能
>
> **最佳实践**：只在确认动画性能瓶颈时才使用 `will-change`。不要对所有元素不加区分地使用 `transform: translateZ(0)` 来强制提升合成层。

## 绘制：

绘制是基于已有的分层，为每一层生成如何绘制的指令集（这里的绘制指令与canvas基本相似，canvas调用的正是浏览器内核的绘制功能）。

> 绘制指令（Paint Records）类似于 Canvas 的绘图 API 调用序列。以一个简单的红色圆角矩形为例，其绘制指令集大致如下：
>
> ```
> Layer: div.card
>   PaintRecord 1: 绘制背景
>     DrawRRect(rect=[0,0,200,100], radius=8, color=#f0f0f0)
>   PaintRecord 2: 绘制边框
>     DrawLineRect(rect=[0,0,200,100], width=1, color=#ccc)
>   PaintRecord 3: 绘制文本
>     DrawText(text="Hello World", x=16, y=40, font="16px sans-serif", color=#333)
> ```
>
> 这些指令是**平台无关的**，不直接调用 OpenGL 或 DirectX。它们描述了“这一层应该长什么样”，具体的像素填充由后续的光栅化阶段完成。
>
> 绘制指令的一个重要特性是**可缓存**。如果一个层的内容没有变化，其绘制指令可以被复用，不需要重新生成。

![image-20260514143417276](/assets/blog_res/2026-05-13-render.assets/image-20260514143417276.png)

完成绘制后，渲染主线程的工作就到此为止，剩余步骤交给其他线程完成。这种优化设计极大提升了渲染整体效率。

![image-20260514143513155](/assets/blog_res/2026-05-13-render.assets/image-20260514143513155.png)

## 分块：

分块（tiling）会将每一层分为多个小的区域，可以用于区分每一层中的渲染优先级，例如会优先将靠近视口的区域绘出。

分块的工作是交给多个线程同时进行的。合成线程也在渲染进程当中，并且合成线程会从线程池取出多个线程来完成工作。

![image-20260515012627896](/assets/blog_res/2026-05-13-render.assets/image-20260515012627896.png)

## 光栅化：

光栅化（raster）是将每个块变为位图，这个过程会优先处理靠近视口的块。

![image-20260515013148687](/assets/blog_res/2026-05-13-render.assets/image-20260515013148687.png)

浏览器会调用gpu进程来完成gpu加速。

![image-20260515013354539](/assets/blog_res/2026-05-13-render.assets/image-20260515013354539.png)

## 画图：

渲染主线程和合成线程都属于渲染进程，渲染进程在一个沙盒中，与操作系统硬件隔离，不受外界干扰。这样的好处是在网页浏览过程中遭受的攻击不会直接影响操作系统，但因此合成线程无法直接联系操作系统硬件，需要通过GPU线程的系统调用才能将quad交给硬件。

![image-20260515194028987](/assets/blog_res/2026-05-13-render.assets/image-20260515194028987.png)

## 最终完整过程：

容易发现，在渲染主线程交付完自己的五个任务给合成线程后（完成他们之间的同步关系），如果有什么操作是只在渲染主线程或者合成线程上进行，是不会影响另一边的线程的。

例如滚动滚动条时，只会影响视口位置，这些操作都可以在合成线程完成，因此即使渲染主线程在忙，也可以正常滚动滚动条。

> 合成线程实现无卡顿滚动的关键在于**分层与光栅化的协同**：
>
> ```
> 用户滚动页面：
>   1. 合成线程收到滚动事件
>   2. 合成线程更新视口位置（只改变 quad 的偏移量）
>   3. 合成线程检查：当前视口附近的块是否已经光栅化？
>      ├── 是：直接合成新画面，输出到屏幕（毫秒级）
>      └── 否：优先光栅化靠近视口的块，逐步更新（可能有短暂空白）
>   4. 整个过程不涉及主线程，JS 和样式计算不受影响
> ```
>
> **为什么 transform 动画也不卡顿**：
>
> ```
> 主线程（繁忙）：执行 JS、计算样式、布局、绘制
>                     │
> 合成线程（独立）：   │
>   读取 transform 值  │  ← 从 GPU 内存中直接读取，不依赖主线程
>   更新 quad 变换矩阵 │  ← 矩阵运算在 GPU 上完成
>   合成新画面         │  ← 不触发 layout 或 paint
>   输出到屏幕         │  ← 60fps 稳定运行
> ```
>
> 这就是 `transform` 动画即使在主线程繁忙时也能保持流畅的根本原因。合成线程与主线程共享 GPU 内存中的纹理数据，但各自独立运行，互不阻塞。

![image-20260515203000307](/assets/blog_res/2026-05-13-render.assets/image-20260515203000307.png)

## 常见面试题：

### 浏览器是如何渲染页面的？

当浏览器的网络线程收到 HTML 文档后，会产生一个渲染任务，并将其传递给渲染主线程的消息队列。

在事件循环机制的作用下，渲染主线程取出消息队列中的渲染任务，开启渲染流程。

-------

整个渲染流程分为多个阶段，分别是： HTML 解析、样式计算、布局、分层、绘制、分块、光栅化、画

每个阶段都有明确的输入输出，上一个阶段的输出会成为下一个阶段的输入。

这样，整个渲染流程就形成了一套组织严密的生产流水线。

-------

渲染的第一步是**解析 HTML**。

解析过程中遇到 CSS 解析 CSS，遇到 JS 执行 JS。为了提高解析效率，浏览器在开始解析前，会启动一个预解析的线程，率先下载 HTML 中的外部 CSS 文件和 外部的 JS 文件。

如果主线程解析到`link`位置，此时外部的 CSS 文件还没有下载解析好，主线程不会等待，继续解析后续的 HTML。这是因为下载和解析 CSS 的工作是在预解析线程中进行的。这就是 CSS 不会阻塞 HTML 解析的根本原因。

如果主线程解析到`script`位置，会停止解析 HTML，转而等待 JS 文件下载好，并将全局代码解析执行完成后，才能继续解析 HTML。这是因为 JS 代码的执行过程可能会修改当前的 DOM 树，所以 DOM 树的生成必须暂停。这就是 JS 会阻塞 HTML 解析的根本原因。

第一步完成后，会得到 DOM 树和 CSSOM 树，浏览器的默认样式、内部样式、外部样式、行内样式均会包含在 CSSOM 树中。

-------

渲染的下一步是**样式计算**。

主线程会遍历得到的 DOM 树，依次为树中的每个节点计算出它最终的样式，称之为 Computed Style。

在这一过程中，很多预设值会变成绝对值，比如`red`会变成`rgb(255,0,0)`；相对单位会变成绝对单位，比如`em`会变成`px`

这一步完成后，会得到一棵带有样式的 DOM 树。

--------

接下来是**布局**，布局完成后会得到布局树。

布局阶段会依次遍历 DOM 树的每一个节点，计算每个节点的几何信息。例如节点的宽高、相对包含块的位置。

大部分时候，DOM 树和布局树并非一一对应。

比如`display:none`的节点没有几何信息，因此不会生成到布局树；又比如使用了伪元素选择器，虽然 DOM 树中不存在这些伪元素节点，但它们拥有几何信息，所以会生成到布局树中。还有匿名行盒、匿名块盒等等都会导致 DOM 树和布局树无法一一对应。

> 从这个角度也可以看到，HTML、CSS、JS 三者对 DOM 的作用是不同层面的：HTML 在解析阶段定义 DOM 的初始结构；CSS 不修改 DOM 节点本身，但通过 `display: none`、伪元素、`visibility` 等决定节点在渲染管线中的呈现方式（操作的是布局树和渲染层）；JS 在运行时通过 DOM API 增删改节点，是唯一能在页面加载完成后继续修改 DOM 树的方式。三者的分工可以概括为——**HTML 定义 DOM，JS 动态改 DOM，CSS 决定 DOM 怎么呈现。**

-----------

下一步是**分层**

主线程会使用一套复杂的策略对整个布局树中进行分层。

分层的好处在于，将来某一个层改变后，仅会对该层进行后续处理，从而提升效率。

滚动条、堆叠上下文、transform、opacity 等样式都会或多或少的影响分层结果，也可以通过`will-change`属性更大程度的影响分层结果。

---------

再下一步是**绘制**

主线程会为每个层单独产生绘制指令集，用于描述这一层的内容该如何画出来。

------

完成绘制后，主线程将每个图层的绘制信息提交给合成线程，剩余工作将由合成线程完成。

合成线程首先对每个图层进行分块，将其划分为更多的小区域。

它会从线程池中拿取多个线程来完成分块工作。

----

分块完成后，进入**光栅化**阶段。

合成线程会将块信息交给 GPU 进程，以极高的速度完成光栅化。

GPU 进程会开启多个线程来完成光栅化，并且优先处理靠近视口区域的块。

光栅化的结果，就是一块一块的位图

---------

最后一个阶段就是**画**了

合成线程拿到每个层、每个块的位图后，生成一个个「指引（quad）」信息。

指引会标识出每个位图应该画到屏幕的哪个位置，以及会考虑到旋转、缩放等变形。

变形发生在合成线程，与渲染主线程无关，这就是`transform`效率高的本质原因。

合成线程会把 quad 提交给 GPU 进程，由 GPU 进程产生系统调用，提交给 GPU 硬件，完成最终的屏幕成像。

### JS 执行和渲染为什么是分开的？

DOM 操作和 DOM 渲染是浏览器事件循环中的两个独立阶段。JS 在宏任务中随便怎么改 DOM，全是改内存里的 DOM 树，浏览器不会立刻渲染：

```
事件循环：
├── 宏任务：执行 JS（随便怎么改 DOM，全在内存里）
│     i=0  div.textContent = 1    ← 只改了内存里的 DOM 树
│     i=1  div.textContent = 2    ← 覆盖上一次的值
│     ...
│     i=99 div.textContent = 100  ← 最终值
│
├── 微任务队列：排空
│
└── 渲染阶段（不一定每轮都触发）：
      layout → paint → composite    ← 这时候才看到 "100"
```

所以循环改 100 次 DOM，浏览器一次都没有渲染，只是改了 100 次内存里的 DOM 树。等 JS 执行完毕、微任务清空后，浏览器在渲染阶段拿到最新的 DOM 树状态，layout + paint 一次出结果。

之前提到的强制回流就是这个机制的例外：如果在改 DOM 之后立即读取 `offsetHeight`，浏览器为了给出准确的布局值，会被迫在当前 JS 执行中插入一次同步 layout——破坏了"改完再渲染"的批处理优化。

### 什么是 reflow？

**reflow 的本质就是重新计算 layout 树**。

当进行了会影响布局树的操作后，需要重新计算布局树，会引发 layout。

为了避免连续的多次操作导致布局树反复计算，浏览器会合并这些操作（浏览器的优化，将这些操作推入同一队列），当 JS 代码全部完成后再进行统一计算。所以，改动属性造成的 reflow 是异步完成的。

也同样因为如此，当 JS 获取布局属性时（同步任务），就可能造成无法获取到最新的布局信息（仍在异步队列中）。

浏览器在反复权衡下，为保证一定能得到最新数据，最终决定在设置属性时不会立即 reflow，但获取属性时立即 reflow。

### 什么是强制回流（Forced Reflow）？

强制回流是 reflow 的一种特殊形式。正常情况下，浏览器会将多次样式修改合并到下一次渲染帧统一进行布局计算，这是一种异步批处理优化。但当 JavaScript 在修改样式后**立即读取需要实时布局信息的属性**时，浏览器被迫立即执行布局计算以返回准确值，这种行为称为强制回流。

用一个例子说明：

```javascript
// 正常回流：浏览器合并修改，只触发一次布局
div.style.width = '200px'
div.style.height = '300px'
// 浏览器在这里统一进行一次布局计算

// 强制回流：读取操作迫使浏览器立即执行布局
div.style.width = '200px'
console.log(div.offsetWidth)  // ← 这里！读取布局属性
div.style.height = '300px'
```

在第二个例子中，`console.log(div.offsetWidth)` 这一行读取操作，迫使浏览器在此时立即执行布局计算，以确保返回的值是准确的。这就是强制回流——原本应该异步批量执行的布局计算，因为 JavaScript 的同步读取需求，被强行提前执行了。

#### 底层机制：浏览器的“脏标志”与异步布局队列

浏览器内部维护着一个“脏布局标志”（dirty layout flag）。当修改一个元素的样式时，浏览器并不会立即重新计算布局，而是做两件事：

1. 将该元素标记为“脏”
2. 在下一个渲染帧的统一布局阶段，一次性处理所有脏元素

这个过程类似于记账：

```
修改样式 → 在账本上记一笔“欠款” → 等到月底统一还款
读取布局 → 必须立即查账 → 被迫当场结清所有欠款
```

假设在一个循环里修改了 100 次元素的宽度：

```javascript
for (let i = 0; i < 100; i++) {
  div.style.width = i + 'px'
}
```

如果每次修改都立即执行布局计算，浏览器就要做 100 次布局。但如果合并到下一次渲染帧统一执行，只需要做 1 次布局。这就是异步队列的优化价值——将 O(n) 次布局合并为 O(1) 次。

强制回流打破了这一优化。当 JavaScript 读取布局属性时，浏览器无法推迟返回值，因为 JavaScript 需要实时的数据来做后续决策。于是浏览器被迫立即清空队列，执行所有待处理的布局计算，然后返回准确值。

```
时间轴 →

正常流程：
  修改 width → [标记脏] → 修改 height → [标记脏] → ... → 渲染帧到达 → [统一布局] → [绘制]

强制回流流程：
  修改 width → [标记脏] → 读取 offsetWidth → [立即布局！] → 修改 height → [标记脏] → ... → 渲染帧到达 → [再次布局] → [绘制]
                                            ↑
                                      这就是强制回流
```

#### 触发强制回流的操作

所有需要实时、准确的布局信息的操作都会触发强制回流，可以分为两类：

**第一类：读取布局属性**

```javascript
// 几何属性
el.offsetWidth / offsetHeight / offsetLeft / offsetTop
el.clientWidth / clientHeight / clientLeft / clientTop
el.scrollWidth / scrollHeight / scrollLeft / scrollTop

// 位置信息
el.getBoundingClientRect()
el.getClientRects()

// 计算样式
window.getComputedStyle(el)
```

**第二类：触发布局的计算方法**

```javascript
// 滚动相关
window.scrollTo()
el.scrollIntoView()
el.focus()  // 聚焦元素可能触发滚动

// 鼠标位置
document.elementFromPoint(x, y)
```

#### 强制回流的连锁反应

强制回流最危险的地方在于它的连锁放大效应。来看一个经典的性能杀手：

```javascript
// 性能灾难：每次循环都触发强制回流
for (let i = 0; i < 1000; i++) {
  div.style.left = i + 'px'        // 写入：标记脏
  console.log(div.offsetLeft)      // 读取：强制回流
}
```

这段代码的执行过程：

```
第 1 次循环：
  写入 left = 0px    → 标记脏
  读取 offsetLeft    → 强制回流（布局 1 次）
  
第 2 次循环：
  写入 left = 1px    → 标记脏
  读取 offsetLeft    → 强制回流（布局 1 次）
  
...

第 1000 次循环：
  写入 left = 999px  → 标记脏
  读取 offsetLeft    → 强制回流（布局 1 次）
```

总共触发了 1000 次布局。而如果写成读写分离的形式：

```javascript
// 读写分离：只触发 1 次布局
for (let i = 0; i < 1000; i++) {
  div.style.left = i + 'px'        // 写入：标记脏
}
console.log(div.offsetLeft)        // 读取：强制回流（只触发 1 次）
```

总共只触发 1 次布局。两者的性能差距是 1000 倍。

#### 浏览器的权衡

你可能会问：浏览器为什么不干脆把所有读取操作也推迟到渲染帧？原因很简单——JavaScript 需要实时的返回值来做决策。

```javascript
// 浏览器无法推迟这个读取
if (div.offsetHeight > 500) {
  // 需要根据当前高度决定后续逻辑
  doSomething()
}
```

如果浏览器推迟了 `offsetHeight` 的返回值，JavaScript 的逻辑就无法正确执行。所以浏览器在性能和正确性之间做出了妥协：

- **写入操作**：尽可能推迟，批量处理（性能优先）
- **读取操作**：必须立即返回准确值（正确性优先）

这个妥协的结果就是强制回流——为了正确性，牺牲性能。

#### 如何避免强制回流

系统性避免策略包括：

1. **读写分离**：将读取操作集中在一起，与写入操作分开
2. **使用 `requestAnimationFrame`**：将写入操作推迟到渲染前执行
3. **使用 `transform` 替代 `top/left`** 做动画
4. **使用 `class` 切换** 替代逐个样式修改
5. **使用文档片段（DocumentFragment）** 批量操作 DOM
6. **离线操作**：先将元素设为 `display: none`，修改后再恢复显示

## 总结

| 概念     | 本质                                               | 触发条件                                           | 代价                       |
| -------- | -------------------------------------------------- | -------------------------------------------------- | -------------------------- |
| 正常回流 | 浏览器在渲染帧统一执行的布局计算                   | 样式修改后，下一次渲染帧到来时                     | 1 次布局                   |
| 强制回流 | 因 JavaScript 读取布局属性而被迫立即执行的布局计算 | 在样式修改后、渲染帧到来前，读取需要实时布局的属性 | 多次布局，可能放大 1000 倍 |

强制回流是浏览器为了满足 JavaScript 对实时布局数据的读取需求，而被迫打破“异步批量布局”优化策略的一种妥协。它的代价是让布局计算的次数从 O(1) 退化到 O(n)，是前端性能优化中需要极力避免的行为。

### 什么是 repaint？

repaint 的本质就是重新根据分层信息计算了绘制指令。

当改动了可见样式后，就需要重新计算，会引发 repaint。

由于元素的布局信息也属于可见样式，**所以 reflow 一定会引起 repaint**。

![image-20260515203718168](/assets/blog_res/2026-05-13-render.assets/image-20260515203718168.png)

### 为什么 transform 的效率高？

**因为 transform 既不会影响布局也不会影响绘制指令，它影响的只是渲染流程的最后一个「draw」阶段**。

由于 draw 阶段在合成线程中，所以 transform 的变化几乎不会影响渲染主线程。反之，渲染主线程无论如何忙碌，也不会影响 transform 的变化。

![image-20260515203737580](/assets/blog_res/2026-05-13-render.assets/image-20260515203737580.png)

如果使用animation，甚至不需要修改cssom树，因此完全不会影响主线程；反过来说，主线程在执行的任务也不会影响这里transform的执行。
